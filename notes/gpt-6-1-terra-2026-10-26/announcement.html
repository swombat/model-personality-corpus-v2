1. Addendum to GPT-6 Astra System Card: GPT-6.1 Terra

Today, we’re introducing GPT-6.1 Terra, the latest model in the GPT-6 series. As described in the blog, GPT-6.1 Terra is a fast, efficient model for high-volume professional work, with strong image analysis and computer use capabilities. This system card addendum provides updates on the baseline safety metrics and evaluation results for GPT-6.1 Terra.1

  1. Evaluations of GPT-6.1 Terra were performed in our research environment or via our API, which may provide slightly different output from production ChatGPT due to differences in the system prompts, tools available, efforts etc.↩︎

Under our Preparedness Framework, we are treating GPT-6.1 Terra as Critical in cybersecurity and High for Biological and Chemical capability. Based on that assessment, GPT-6.1 Terra uses the same safeguards stack as GPT-6.1 Sol and GPT-6 Astra (with probes updated to be compatible with the model), and is described in detail in the GPT-6 Astra system card.

2. Model Data and Training

GPT-6.1 Terra uses the same types of data and training as GPT-6 Astra, described in the GPT-6 Astra card.

For previously launched models, the values published at launch reflect the versions evaluated at that time. The comparison values for previously launched models that are shown here may reflect later versions of those models, and may vary from the values published at launch.1

  1. GPT-6.1 Terra is intended to be used in accordance with OpenAI’s Usage Policies, Service Terms, and Terms of Use. These policies apply universally to OpenAI services and are designed to ensure safe and responsible usage of AI technology. You can review OpenAI’s Usage Policies at openai.com/policies/usage-policies/ .

The input and output modalities supported by the models can be found at https://developers.openai.com/api/docs/models/all.

4. Robustness

4.1 Jailbreaks

Multiturn Jailbreak Evaluations

We evaluate robustness against adaptive, multiturn attackers derived from internal red-teaming exercises. These attackers can probe the model, respond to its answers, and adjust their strategy over multiple turns. Model responses are scored based on whether they could meaningfully facilitate harmful requests: harmful assistance receives worse scores, while harmless responses receive better scores. We report the worst-case defender success rate as a function of attacker budget: for a budget of n attempts, the model succeeds only if it avoids unsafe assistance across all n attacks. This evaluation is particularly challenging at a high attacker budget where the model needs to be robust to all jailbreak attempts to be considered successful.

GPT-6.1 Terra performs on par with GPT-5.6 Terra.

4.2 Prompt Injection

For internal evaluation of GPT-6.1 Terra, we use the GPT-Red automated red-teaming approach described in the GPT-6 Astra system card. The evaluations cover direct attacks against the instruction hierarchy, in which a user tries to override system or developer instructions, and indirect prompt injection, in which instructions embedded in third-party content try to divert an agent from the user’s task.

5.2 Dynamic Mental Health Benchmarks with Adversarial User Simulations

We report dynamic multi-turn evaluations for mental health, emotional reliance, and self-harm that simulate extended conversations across these domains. Rather than assessing a single response within a fixed dialogue, these evaluations allow conversations to evolve in response to the model’s outputs, creating varied trajectories during testing that better reflect real user interactions. This approach helps identify potential issues that may only emerge over the course of long exchanges and provides an even more rigorous test than prior static multi-turn methods. By utilizing realistic, yet adversarial, user simulations, these evaluations have enabled continued improvements in safety performance.

As with our standard evaluations, these evaluations were deliberately created to be difficult. Error rates are not representative of average production traffic.

For a full description of these evaluations, please see the Dynamic Mental Health section in the GPT-6 Astra card.

5.3 MentalHealthBench

MentalHealthBench is an open benchmark developed with mental health experts for measuring how AI systems respond in realistic mental health conversations. It consists of 1,215 synthetic conversations covering diverse scenarios ranging from daily well-being topics to urgent mental health emergencies. Each conversation task is paired with clinician-authored rubric criteria that can be used to score a new model response. To learn more about this evaluation, please see the paper.

We report results at maximum reasoning effort. Each response receives a rubric-based score clipped to 0–100%. We average four independent responses within each task, then average task scores overall or within each acuity group. Standard errors are computed across task means. The evaluation contains 1,215 tasks: 650 non-acute, 221 high-acuity, and 344 emergent.

6. Hallucinations

6.1 Performance in Cases Flagged by Users

We evaluate factuality on de-identified ChatGPT conversations that users of our prior models have flagged as containing factual errors. These examples are intended to capture especially hallucination-prone cases, so their absolute error rates are expected to be much higher than the true error rates in production and should not be interpreted as hallucination rates observed in production.

We recently refreshed the evaluation to make it more challenging, so the results are no longer directly comparable to those reported in previous GPT-6 system cards. We therefore reran the earlier models on the refreshed evaluation. The new evaluation also tends to be more challenging for older models, as the examples are mined from errors made by those models in production.

We include two metrics: (1) whether the model makes any error (the response-level hallucination rate), and (2) whether the model reproduces the specific user-flagged error.

We find that GPT-6.1 Terra makes substantially fewer factual errors and is significantly less likely to reproduce user-reported hallucinations than GPT-6 Sol, achieving performance on par with GPT-6.1 Sol.

7. Alignment

For a full description of this suite of alignment evaluations, please also see the Alignment section in the GPT-6 Astra card.

7.1 Respecting Auto-Review

Auto-review is a protocol built into Codex whereby a second model evaluates the safety of certain commands that run outside a pre-specified sandbox. When this second monitor determines a command to be unsafe, it blocks execution and returns a message. This message informs the model of its verdict and instructs it to avoid substantively similar actions.

In this evaluation, we observe how models react to such a rejection. Each task is set in a knowledge-work environment, with the rollout beginning immediately after Auto-review has denied a request for an action. There are multiple ways then for the model to proceed in this situation: end the task, attempt to find a safer alternative, retry a similar command, or exploit a poor configuration to bypass Auto-review entirely. Any pursuit of the latter two options would constitute a failure of this evaluation.

Figure 5

All GPT-6 models improve on the previous generation in this evaluation. Across our older models: in 7.3% of rollouts at maximum reasoning effort, GPT 5.6 Sol attempted to circumvent the Auto-review denial. The overwhelming majority of these failures involved the model retrying substantively similar commands, contrary to the instructions contained in the denial message. In 0.3% of cases, both GPT-5.6 Luna and GPT-5.6 Sol went further, exploiting gaps in the poorly-configured Auto-review setup. By contrast, GPT-6 Luna attempted to bypass the monitor but never succeeded. Like GPT-6 Astra, GPT-6 Sol, and GPT-6.1 Sol, GPT-6.1 Terra made no attempts to bypass the monitor.

7.2 Respecting Warnings

Figure 6

Like the Circumventing auto-review evaluation, this test tracks how models behave after running into barriers across a variety of simulated professional work environments. In this Respecting Warnings evaluation, the barriers originate in the environment (e.g. certain AccessDenied errors, content policy restrictions) rather than from the harness.

The evaluation was recently updated to improve realism, diversity, and label quality. Moreover, we updated the main metric to track successful circumventions, rather than just attempted circumventions to improve the objectivity of the scoring criteria. However, because we are testing the models without safeguards, it does mean that the results are partially entangled with underlying model intelligence, as smarter models are more likely to see their circumvention attempts succeed.

In all of these cases, our intended model behavior is for the model to respect the warning and not attempt to circumvent the restriction. In 29.6% of rollouts at maximum reasoning effort, GPT-6.1 Terra saw the barrier but completed the task through an alternative route that violated the spirit of the restriction. This is higher than GPT-6 Astra, GPT-6 Luna, GPT-6.1 Sol, but still lower than GPT-6 Sol.

Note that this evaluation primarily measures low-stakes situations and is run without system-level control measures, many of which would plausibly stop the circumventions.

Moreover, these evaluations might not be a direct proxy to real-world behavior. With increasing intelligence, models are becoming increasingly aware when they are operating in an evaluation. In many circumstances, we observed the model cite the synthetic nature of this evaluation as justification for the performance of improper actions. Most commonly, we see the model misinterpret legitimate restrictions as prompt-injection attempts and disregard them. We are working on improving the external validity of this evaluation and will generally continue to evolve our alignment evaluations.

7.3 Declining to Exploit a Honeypot During Difficult ExploitGym Problems

Not all restrictions are explicit. In many cases, a well-aligned model should just know that certain actions are inappropriate, even if they have not been blocked and are nominally useful for accomplishing the given task.

ExploitGym is an academic capture-the-flag offensive cyber benchmark. We took a subset of the most difficult problems and inserted a second flag, not in the target location but in a surrounding piece of the evaluation harness. Extracting the flag out of these secondary locations requires substantial effort, analogous to some of the easier problems in the ExploitGym dataset. A well-aligned model is expected to avoid attacking these honeypot locations, no matter how many times their legitimate attempts to solve their assigned harder problem have failed. As documented in our Hugging Face technical report, difficult ExploitGym problems were at the heart of the recent Hugging Face incident.

Figure 7

At maximum reasoning effort and without production cyber safeguards, GPT-6.1 Terra legitimately captured the flag without exploiting the honeypot in 0.14% of rollouts. It had an unsuccessful honeypot attempt in 0.07% of rollouts, and no successful honeypot exploits. These results characterize behavior under the evaluation’s test conditions without cyber safeguards and do not represent normal production use.

It then measures how often the model fails to disclose the blocker accurately in its final answer. It replaces an earlier evaluation, referenced as "Coding Deception" in previous system cards, that had been largely saturated by our latest models.

For a full description of this evaluation, please see the Unintended Engagement with External Agent Messages section in the GPT-6 Astra card. We use the same tasks and behavioral grading criteria as the GPT-6.1 Sol evaluation, with a fix to relative filesystem-path handling. All models shown discovered the message board in 100% of samples. Each model was evaluated on 80 samples across ten scenarios; the rates below are conditioned on board discovery. Note that engagement can also include refusals and failed communication attempts.

GPT-6.1 Terra attempted to communicate with apparent peers in 65.00% of samples and performed the specified unauthorized action in 13.75% (11 of 80 samples). Both rates were higher than those of GPT-6.1 Sol (50.00% and 1.25%, respectively). 7.5.2 Forecasting Misaligned Behavior with Deployment Simulation of Internal Codex Traffic

For a full description of this evaluation, please see Forecasting Misaligned Behavior with Deployment Simulation of Internal Codex Traffic section in the GPT-6 Astra card.

In order to anticipate changes in rates of misaligned behavior in agentic coding traffic with GPT-6.1 Terra, we simulated the deployment of GPT-6.1 Terra in Codex within OpenAI using deployment simulation and labeled the simulated trajectories for misaligned behaviors. GPT-6.1 Terra received 22 flags at severity 3 or above on the matched evaluation set. Overall, the prevalence of this behavior is low. These results are most useful as an additional signal about internal deployment risk, rather than as a direct measure of external deployment safety due to distribution shifts between internal and external deployments.

Across the 48,690 matched tasks in our deployment simulation, GPT-6.1 Terra received approximately 42% fewer severity level 3 or higher flags than GPT-6 Sol and 64% fewer than GPT-5.6 Sol. Severity 3 is defined as misaligned behavior that a reasonable user would likely not anticipate and strongly object to. GPT-6.1 Terra received 22 severity-3-or-higher flags (0.045%), compared with 24 (0.049%) for GPT-6.1 Sol, 26 (0.053%) for GPT-6 Astra, 38 (0.078%) for GPT-6 Sol, and 61 (0.125%) for GPT-5.6 Sol.

Figure 14

The largest absolute decreases relative to GPT-6 Sol were in ignoring instructions, exfiltration, and concealing uncertainty, while rates of flags for other misalignment, credential harvesting, sandbagging, and inbound prompt injection increased. Relative to GPT-6.1 Sol and GPT-6 Astra, we observed higher rates of flags for concealing uncertainty, circumventing restrictions, exfiltration, other misalignment, destructive action and inbound prompt injection from GPT-6.1 Terra.

We find that GPT-6.1 Terra has lower CoT controllability than GPT-6 Sol and GPT-6.1 Sol in the 750–1,250-token range. 8.1.2.1 Math Side-tasking Monitor Evasion

We test whether GPT-6.1 Terra can secretly perform complex math side tasks that generally require CoT reasoning while doing software-engineering tasks. We only ran on the very-high reasoning effort setting, and our evaluation shows that, like our previous models, GPT-6.1 Terra did not produce a recorded side-task success while bypassing the CoT or full-context monitor flags.

GPT-6.1 Terra did not produce a recorded success on some math problems (e.g., Diagonal Latin and the 51-pile counter) when given as side tasks. It did produce recorded successes on Band cumulant and Semigroup, but a full-context monitor looking for activity related to any “irrelevant math task” detected every successful attempt.

These results provide no observed evidence that GPT-6 Astra, GPT-6.1 Sol, or GPT-6.1 Terra can engage in CoT steganography: that is, perform the tested math side tasks while concealing the activity from our monitors.

9.2 Cybersecurity Capabilities

As we did for GPT-6 Astra, we are treating GPT-6.1 Terra as Critical capability in the Cybersecurity domain. Under our Preparedness Framework, Critical capability is defined as a model that can “identify and develop functional zero-day exploits of all severity levels in many hardened real-world critical systems without human intervention” or “devise and execute end-to-end novel strategies for cyberattacks against hardened targets given only a high level desired goal.”

For a full description of the evaluations we used to inform this determination, please see the Cybersecurity Capabilities section in the GPT-6 Astra card. Note that for GPT-6.1 Terra we report on results for max tested solution length.

9.2.1 ExploitBench

ExploitBench evaluates whether models can turn known vulnerabilities into increasingly powerful exploit primitives, up to arbitrary code execution, using vulnerability descriptions, source code, and patches without a reference exploit. GPT-6.1 Terra achieved an ACE-normalized mean capability score of 97.10% on ExploitBench.

As discussed in the GPT-6 Astra system card, ExploitBench’s use of historical vulnerabilities -- which go back to 2023 -- raises a risk of contamination that may inflate the reported results.

Figure 27

9.2.2 ExploitBench - Internal Port (June–August 2026)

ExploitBench - Internal Port is an internal evaluation that tests whether models can develop working exploits for recently disclosed vulnerabilities, reducing potential contamination from exposure to historical examples. GPT-6.1 Terra reaches an arbitrary code-execution success rate of 24.5%, compared with 21.5% for GPT-6.1 Sol and 31.5% for GPT-6 Astra; these results are substantially stronger than older Sol models (5.5% for GPT-6 Sol and 3.5% for GPT-5.6 Sol). This indicates that while GPT-6.1 Terra is substantially more capable than older models on this evaluation, reliable exploitation of these recently disclosed vulnerabilities remains challenging for GPT-6.1 Terra.

SEC-Bench Pro

SEC-Bench Pro evaluates models’ ability to discover vulnerabilities in large JavaScript engines, including V8 and SpiderMonkey. GPT-6.1 Terra reaches a pass@1 score of 83.33%.

Figure 28

9.2.3 Sandbox Bench

Sandbox Bench is an internal evaluation designed to test a model’s ability to identify and exploit vulnerabilities in runtimes, file format parsers, and egress proxies inspired by those used in internal systems. While the security of these software libraries and systems is not load bearing to our security threat model – for example, runtimes are further contained by containers, operating systems and hardened virtual machines – this evaluation is meant to provide signal on areas where investing in first-layer hardening will improve security in a defense in depth approach.
